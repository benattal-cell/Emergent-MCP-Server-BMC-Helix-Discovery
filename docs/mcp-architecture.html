The problem

The data already exists. The answers are locked behind expertise.

BMC Helix Discovery continuously maps every host, software instance, network device, container and business service in the estate — a goldmine for security, audit, finance and architecture teams. But extracting an answer means writing Discovery DSL, knowing the exact node kinds and traversal paths, and reading raw query output. In practice, every question becomes a ticket to a small group of specialists.

🔒

Knowledge bottleneck

Only a handful of people can write the DSL. Business stakeholders wait days for a number that already exists in the database.

🧩

Wrong-tool / hallucination risk

Hand an LLM raw database access and it invents node kinds and relationships that don't exist, returning confident but wrong answers.

⏱️

Decisions can't wait

A new CVE drops, an audit lands, a cloud-migration business case is due. These need answers now, in natural language, with evidence.

💡
The design bet: wrap Discovery behind the Model Context Protocol with opinionated, guard-railed tools — so any compliant AI client can answer business questions safely, and the AI is steered away from improvising bad queries.

The virtualization licensing trap

Under Oracle's and Microsoft's virtualization rules, a single VM that could migrate across an ESX cluster can make the entire farm licensable. One mis-mapped dependency, one unpinned VM — and you license dozens of hosts you never meant to, or pay twice for the same server.

DORA — now enforced

Under the EU Digital Operational Resilience Act (applicable since Jan 2025, active enforcement from 2026), financial entities face fines up to 2% of total worldwide turnover — some national transpositions reach 10% — plus up to €1M personal liability for executives. Running unsupported software is a resilience finding.

Technology choices & rationale

Every dependency earns its place

Click each choice to see the trade-off it resolves. The recurring theme: minimize the attack/maintenance surface, maximize how reliably a non-expert AI can drive Discovery.

Model Context Protocol (MCP)@modelcontextprotocol/sdk 1.29+

Why: one open protocol means any compliant client (ChatGPT, Claude, Mistral…) connects from just a URL — no per-client integration. MCP's three primitives map cleanly onto the need: Tools (the AI acts), Resources (the AI reads), Prompts (the user launches a workflow).

Node.js 20 + pure TypeScriptFastAPI/React removed+

Why: the project deliberately collapsed an earlier React + FastAPI design into a single TypeScript runtime. One language end-to-end, one process to deploy and secure, and the MCP SDK is first-class in TS. Static typing + compile step catch schema/contract drift before runtime.

Streamable HTTP transport (remote)deployable online+

Why: a remote HTTP server (vs a local stdio one) can be hosted once (Emergent/Railway) and shared by many users and clients, with centralized auth and updates. Endpoints are mirrored under /api/* to satisfy preview-environment routing.

OAuth 2.1, self-hostedPKCE · DCR · refresh rotation+

Why: static bearer tokens leak and never rotate. The server acts as its own authorization server so clients onboard with zero manual config (Dynamic Client Registration), use authorization_code + PKCE S256, and rotate refresh tokens. An optional shared-password consent gate adds friction only when you want it.

Zod schemaszod 3.25+

Why: every tool input is a Zod schema — it doubles as runtime validation and as the JSON Schema advertised to the AI. The model sees exactly which parameters exist (with closed enums), which is the first line of defense against hallucinated arguments.

Guard-railed DSL pipelinebuild_query → execute_dsl+

Why: letting an LLM write Discovery DSL freely produces invented kinds and relationships. So raw DSL is fenced: build_query composes from structured intent and validates, execute_dsl re-checks clause ordering and referenced kinds against the live taxonomy before running, and a curated common_relationships referential supplies only real traversal paths. An expert-curated DSL cheat-sheet — hand-written by a Discovery expert, not an auto-generated grammar — is embedded in the tool description and exposed as a resource.

Visual rendering pipelineresvg · graphology · cytoscape · d3+

Why: answers land better as pictures. Tools emit SVG, rasterized to PNG with @resvg/resvg-js (no headless browser). Dependency graphs use ForceAtlas2 (graphology) — chosen to replace a Graphviz dependency — plus Cytoscape/d3 for an interactive, self-contained HTML graph. Output is tunable via env vars for token-frugal, text-only deployments.

Server-side limits & CSV knowledge basepolicy + grounding+

Why: result size is governed server-side (MCP_RESULT_LIMIT) with offset pagination (hasMore/nextOffset) so the AI can't invent per-call limits. IT-cost answers are grounded in a CSV reference catalog loaded at startup — the single source of truth, with no live pricing guesswork.

Rendering & token cost

Why three graphics libraries — and what each one costs in tokens

A picture lands better than a table, but every byte a model ingests is billed. Here's the honest breakdown: which library does what, which choices are validated, where a redundancy hides, and what each visual actually costs on Claude Sonnet 4.6.

🧲

ForceAtlas2

✓ validated

graphology, server-side. Positions nodes for the static PNG/SVG with no browser. Replaced Graphviz → pure-JS, no native binary, deterministic.

🖼️

resvg

✓ validated

@resvg/resvg-js (Rust). Rasterizes SVG→PNG with no headless Chromium — tiny, fast, container-friendly. Excellent fit.

🕸️

Cytoscape

✓ earns its weight

Client-side interactive mesh. Pan/zoom, neighbor spotlight, mini-map, search, legend, dark mode — all native. Re-deriving this in raw code would be hundreds of lines.

🌳

D3

△ redundancy

Client-side service tree (d3.hierarchy/tree). Prettier tree — but Cytoscape's breadthfirst layout already renders hierarchies, so two graph engines ship where one could do.

⚖️
The honest trade-off: the static-layout (ForceAtlas2) and interactive-layout (Cytoscape) split is genuinely justified — the PNG needs server positions, the browser view needs a live layout. D3 is the one true double-employment: it only renders the service-architecture tree, which Cytoscape's breadthfirst layout could already cover. Keeping D3 buys a nicer tree at the cost of inlining a second graph engine (~280 KB) on every mode=service response. A defensible call — but worth naming.

Same answer, four shapes — because LLM clients don't render alike

This is exactly why the server emits a PNG and an SVG (and an HTML resource, and always text): no single representation renders everywhere, and the cost profile differs by client.

The token-burn signal to manage: the PNG costs a fraction of a cent and works everywhere. The tool description already says "do not summarize the raw HTML — it is meant for rendering", and the per-deployment env flags (MCP_DEFAULT_VISUAL, MCP_INCLUDE_SVG) tune what's emitted. Inputs & outputs

Three MCP primitives — who drives what

The server speaks the full MCP vocabulary. Understanding which primitive does what explains the entire input/output contract.

⚙️

Tools

the AI acts

16 callable tools. In: a Zod-validated JSON object. Out: a text summary + structuredContent + an optional PNG/SVG visual.

  • Always read-only against Discovery
  • Every response carries a headline summary
  • Errors are normalized & secret-redacted
📚

Resources

the AI reads

Pull-on-demand reference content the model can fetch.

  • mcp://discovery/dsl-cookbook — an expert-curated DSL reference (a Discovery expert's hand-written summary + examples, not a formal grammar)
  • A Cytoscape UI resource backs the interactive graph view
  • Same single source that's embedded in tool descriptions
🎬

Prompts

the user launches

User-triggered workflows (e.g. client slash-commands) that pre-wire the correct tool sequence.

  • cve_impact · value_review
  • eol_audit · dependency_analysis
  • Keep the AI on the documented path instead of improvising

A single tool call, end to end

1

Validate input

The raw JSON is parsed by the tool's Zod schema — unknown or malformed args are rejected before anything runs.

2

Compose & verify

The handler builds a Discovery query and verifies referenced kinds/relationships against the live taxonomy.

3

Call Discovery

Through the one client: POST /api/<ver>/data/search, bearer-authenticated, 30s timeout, offset pagination.

4

Shape the result

Flatten rows, compute a headline summary, render an SVG→PNG visual when relevant.

5

Return MCP payload

content[] (text + image) and structuredContent the client can render or chain.

Example — a CVE exposure briefing

{
  "name": "discovery_cve_executive_summary",

// 2 · the server returns
{
  "content": [
    { "type": "text",  "text": "42 assets exposed…" },
    { "type": "image", "data": "<PNG>" }

    "topServices": [ … ],
    "topHosts": [ … ]

Security & deployment

Safe by construction, deployable anywhere

🔑

No static secrets

Nothing sensitive is committed. Configuration comes entirely from environment variables; OAuth replaces any static bearer to /mcp.

🧽

Secret redaction

Keys like token, password, authorization, api_key are scrubbed from every error and log. The Discovery Authorization header is never echoed back.

👁️

Read-only by default

Tools are annotated readOnlyHint / openWorldHint. The server queries Discovery; it never writes back to the estate.

🚦

Bounded & timed

1 MB request-body cap, 30s outbound timeout, server-side result limits with pagination — the AI can't run away with the query.

Remote & portable

A single node dist/index.js listening on $PORT, mirrored /api/* routes, and a /health probe — runs on Emergent, Railway, or any container host.

🎛️

Tunable output

MCP_DEFAULT_VISUAL and MCP_INCLUDE_SVG trade richness for token cost — full visuals, PNG-only, or text-only for frugal LLM deployments.

Connecting a client

With OAuth, a compatible MCP client needs only the URL — it discovers the authorization server, registers itself, and runs the flow automatically.

{
  "mcpServers": {
    "bmc-helix-discovery": {
      "url": "https://your-server.example.com/mcp"
    }
  }
}
